# 伐木村民会不会无新操作转去挖矿？

日期：2026-10-02。调查版本：`35e12b8f3b48b31823cfa9fb2b5a582dacffe586`。
本目录仅增加 PoC、运行器和证据，未修改游戏逻辑。

多人补充：[50～400 名伐木村民、最多 600 个单位的拥堵 PoC](crowd-report.md)。

**在玩家村民没有排队指令的前提下，本次没有复现自动从伐木切到采金／采石。**
树耗尽后，村民只会续采同类木材；附近没有符合条件的树就闲置。
**“当时没有再操作，但后来自己去挖矿”可以复现，前提是已有挖矿队列，或已有建造采矿营的队列。** 这并不能证明用户实际遇到的情况一定由队列造成。

## 覆盖与结果

每轮 58 个场景、326 项检查；连续两轮全部通过。52 个不应挖矿的场景没有出现采矿目标；6 个对照场景成功采矿。输出保存于 [汇总](results/summary.json)、[第一轮完整记录](results/run-1.json)、[第二轮完整记录](results/run-2.json) 和对应 `.log`。
每轮累计运行 2,020 模拟秒。测试脚本、相关生产脚本与引擎的 SHA-256 保存于 [版本清单](results/source-manifest.json)。

| 场景 | 数量／轮 | 结果 |
| --- | ---: | --- |
| 三种实际支持的文明 × 八种资源状态 × 金／石矿 | 48 | 空队列下没有转采矿；矿量与玩家金石收入均未变化 |
| 正常开局，保留敌方 AI、迷雾与全部模拟，每张地图观察两个初始伐木村民 120 秒 | 2 | 没有转采矿，木材持续增加 |
| 新的非排队伐木指令清除旧采矿队列：单位入口与玩家右键分发入口各一个 | 2 | 树耗尽后闲置，没有采金 |
| 已排队采金／采石：单位入口两个，玩家右键分发入口一个 | 3 | 树耗尽后执行既有采矿队列 |
| 低层 `order_gather()` 保留已有采金队列 | 1 | 树耗尽后采金；这是 API 对照，不是玩家右键的行为 |
| 排队建造采矿营 | 1 | 树耗尽 → 建营 → 完工自动采金 |
| 敌方 AI 村民，没有队列，木材耗尽且只剩金矿 | 1 | 闲置后由敌方 AI 分配采金 |

八种资源状态：原树仍有大量木材；耗尽后附近有树；附近只剩矿；下一棵树距离 185、超出续采半径 180；原目标 `queue_free()`；原目标立即 `free()`；替代树未探索而矿已探索；地形墙使替代树不可达。
迷雾案例固定探索状态，并暂停迷雾更新来保持测试前提；其他沙盒案例关闭迷雾。两张正常开局地图使用种子 `4242`、`44127`，保留默认迷雾和敌方 AI。

## 复现时间线

以下时间为模拟秒；所有指令都在开始时设置，之后不再发送指令。

| 对照 | 初始状态 | 后续变化 |
| --- | --- | --- |
| 排队采金，含玩家右键分发入口 | 砍 100 木材，队列中已有采金；附近还有别的树 | `15.45s` 原树耗尽，目标变金矿；40 秒共收到 100 木材、198 黄金 |
| 排队采石 | 砍 100 木材，队列中已有采石 | `15.45s` 目标变石矿；40 秒共收到 100 木材、154 石材 |
| 排队建采矿营 | 砍 25 木材，队列中只有建营任务 | `3.35s` 开始建营，`9.65s` 完工后自动采金 |
| 敌方 AI | 砍 25 木材，空队列，地图无其他木材／食物 | `3.35s` 闲置，`6.15s` AI 分配采金 |

低层 `order_gather()` 的对照显式构造了“先排队采金，再直接开始伐木”的状态。该入口保留队列；生产代码的玩家右键入口使用 `issue_command(..., append_order)`，不排队时会清空旧队列。不能把这个 API 对照直接归因于正常玩家操作。

## 代码依据

- [unit_work.gd](../../scripts/entities/unit_work.gd)：`continue_gather()` 先执行已有队列；否则以 `gather_kind` 查找同类资源，没有就结束任务。`finish_construction()` 在采矿营完工后选择附近金矿／石矿。
- [game.gd](../../scripts/game.gd)：`find_nearest_resource()` 要求 `resource.kind == kind`；`start_game()` 只给阵营 `1..N-1` 创建 AI，玩家阵营 `0` 没有 AI 控制器。
- [unit_orders.gd](../../scripts/entities/unit_orders.gd)：非排队 `issue()` 清空旧队列；`start()` 不清空；进入采集任务时从目标更新 `gather_kind`。
- [player_orders.gd](../../scripts/player/player_orders.gd)：玩家右键上下文分发调用 `issue_command()`，传入是否排队的标志。
- [ai_controller.gd](../../scripts/ai/ai_controller.gd)：敌方 AI 会给闲置村民重新分配资源。这是敌方行为，不代表玩家村民有自动经济接管。

## 运行

从项目根目录执行：

```sh
python3 poc/gather-switch-poc/run.py
```

默认运行两轮，使用 `make run` 同款本地 Godot 4.7.2 引擎，覆盖 `results/` 的日志与 JSON。可指定其他输出目录或引擎：

```sh
python3 poc/gather-switch-poc/run.py --runs 1 --output /tmp/gather-switch-poc
python3 poc/gather-switch-poc/run.py --godot /path/to/godot
```

[测试脚本](gather_switch_poc.gd) 调用生产环境 `game.step(0.05)`，包含导航任务、AI 和实体处理，每个模拟步检查目标与队列，并定期推进真实事件循环以释放耗尽资源和完成异步任务。沙盒额外检查矿量及资源收入，避免只根据动画判断。正常开局中玩家本来有其他采矿村民，因此按被观察的两个伐木村民的目标判断，不把全阵营黄金收入误算成它们的收入。

[运行器](run.py) 同时检查进程退出码、脚本错误、失败检查、结果文件和结束标记；脚本断言中止、报告缺失或超时都不会误报成功。

这是确定场景的无窗口逻辑验证，未捕获用户真实游玩的输入、选择状态和历史队列，也未穷举全部地图、多人碰撞、战斗中断与输入时序。结果支持“这些空队列场景没有自动跨资源续采”，不能证明所有情况下绝对不可能，也不能证明用户曾下过某条指令。
