## 测试设置的纠正

没有删除或改为“预期失败”任何已确认问题的断言。修正了两个原来依靠穿障才通过的测试设置：

- 状态 PoC 的一个农田对照伸进了船体。把该对照移回陆地，增加三个船体起点合法性断言；原本复现岸边农田占用问题的另一变体保留。
- `economy_siege_controls` 把士兵直接放在攻城塔右侧的不可走地形内。现在先选合法位置并断言，再检查登乘；新隔墙登乘测试仍要求失败。

另增加一项连续排队 2,048 条失效采集任务的检查，验证失败处理不会递归耗尽调用栈。状态 PoC 因此从 226 项增加到 230 项，边界 PoC 仍为 818 项。两个 PoC 已纳入默认 `tools/check_navigation.py`。

## 性能处理

开发中发现，逐个匹配落点调用全图后备寻路，会让 400 单位下令耗时显著增加。编队现在复用“成员能到达其目标”的证明，并缓存目标到落点的检查；当一个编队偏移无法快速验证时，选择附近可验证的落点。玩家实际目标的完整细网格／几何后备搜索继续保留。

所有性能数字来自无窗口 CPU 模拟，不代表渲染 FPS。前后测量依次运行，使用同一引擎与 180 步设置（战斗脚本固定 90 步）。[修复前日志](repairs-20260929/performance-before/results.json)、[修复后日志](repairs-20260929/performance-after/results.json)。

连续碰撞与拥堵恢复有实际 CPU 开销，不能宣称性能完全没有回退。独立移动基准的工作负载保持一致；真实场景中的出生落点、路径与拥堵恢复行为已经改变，战斗次数也会变化，因此不能把战斗总耗时之比当作单次攻击的速度比。混合障碍中 400 单位的模拟峰值仍然较高，需要后续针对恢复调度和几何后备图继续优化。

| 无窗口测量 | 修复前 | 修复后 |
| --- | ---: | ---: |
| 400 单位独立移动平均帧时间 | 4.64 ms | 5.24 ms |
| 400 单位独立移动 P95 | 6.29 ms | 5.37 ms |
| 400 单位编队下令 | 118.90 ms | 196.00 ms |
| 混合障碍中 400 单位平均帧时间 | 38.10 ms | 61.60 ms |
| 混合障碍中 400 单位 P95 | 50.30 ms | 192.90 ms |
| 混合障碍中 400 单位峰值 | 562.00 ms | 771.10 ms |
| 200 对 200 战斗平均帧时间 | 2.71 ms | 18.90 ms |

战斗实际攻击次数为修复前 1204、修复后 1166；严格出生落点改变了部分单位的接敌路线。
