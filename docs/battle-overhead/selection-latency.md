# 围攻拖选框停顿 PoC

2026-09-29，M2，自带 Godot 4.7.2 debug template。验证提交 `9782cfc` 的后台恢复寻路是否造成偶发拖选卡顿。

**复现了拖选更新停顿，但未复现拖选状态卡死。** 关闭后台恢复仍有明显停顿；当前数据不支持将问题全部归因于新增后台队列。开启后台后也仍有 75–91 ms 的更新间隔，不能声称拖选已经流畅。同步射程寻路是已捕获的一个阻塞来源；另外一些长帧尚未归因，尚未排除线程竞争、其他游戏逻辑或系统调度。

## PoC 如何验证

`tests/selection_battle_latency_poc.gd` 复用实际 2.5D 场景：80 人集中围攻 6 座建筑，旁边新增 8 只鹿，保留原地图实体。每 1.5 秒自动完成一次拖选，按住 1.2 秒后松开。鼠标位置由单调时钟生成，不注入 sleep 或人工计算负载。

诊断子类仅替换系统指针、按键和无窗口模式的焦点输入，运行生产 `_advance_selection_pointer`、`_update_selection_drag`、选择结算和真实四边框 Control。逐次检查框的位置、可见性、tracking/active 状态、第一条边位置和松手隐藏。记录：

- 两次按住期间的鼠标轮询间隔，表示拖选逻辑多久不能更新。
- 轮询/更新本身、后台队列、根游戏回调、整帧模拟、移动碰撞和同步导航耗时。
- 超过 40 ms 的更新间隔以及**前一帧**的操作，避免将停顿归因于恢复后的轻量帧。
- 后台任务数量、释放次数、框状态不匹配数、建筑伤害；窗口模式另记录 frame_post_draw 间隔。

新文件 `tools/profile_selection_latency.py` 串行跑空闲控制和同步/后台/后台/同步对照，每次 12 秒，统计相邻轮询均在前 2 秒之后的按住样本。冷启动跨越预热边界的长帧单独记录。工具检查源码指纹，源代码在 A/B 期间变化会拒收结果。

工作区同时有其他建筑尺寸修改，因此正式数据使用 `9782cfc` 的隔离副本，含同版本 data、assets、scripts 和资源导入缓存，只加入 PoC 及测试用游戏工厂。工作区混合版本的试跑不计入以下结果。

## 固定版本实测

原始事件和时序见 [selection-latency.json](selection-latency.json)。这里均为 **headless 合成指针**，不是屏幕呈现延迟，也不是物理鼠标到画面的端到端测量。

| 场景 | 按住样本 | 更新间隔 P95 / 最大 | 超过 40 ms 次数 | 队列最大耗时 | 状态错误 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 空闲，后台开启 | 934 | 9.69 / 59.46 ms | 1 | 0.06 ms | 0 |
| 围攻，同步，第 1 轮 | 499 | 36.26 / 180.31 ms | 19 | 0 | 0 |
| 围攻，后台，第 2 轮 | 501 | 31.22 / 91.29 ms | 13 | 3.41 ms | 0 |
| 围攻，后台，第 3 轮 | 583 | 24.16 / 74.77 ms | 7 | 0.94 ms | 0 |
| 围攻，同步，第 4 轮 | 564 | 28.24 / 85.93 ms | 16 | 0 | 0 |

围攻各轮均完成 7 次释放，建筑伤害为 810 / 780 / 870 / 800；后台两轮分别提交 171 / 178 个任务。拖选轮询与更新本身的 P95 为 0.017–0.024 ms。既有 `selection`、`build_selection` 测试也通过。

具体事件：

1. 同步版本一次更新间隔 **180.31 ms**，前帧模拟 **178.63 ms**，其中同步搜索 **158.47 ms**，移动碰撞 **6.77 ms**。此时后台完全关闭。另一冷启动间隔 **2558 ms**，记录到单次 `path_to_range` **1522.77 ms**。
2. 后台版本一次间隔 **72.94 ms**，前帧模拟 **71.29 ms**，其中 `path_to_range` **48.48 ms**、移动碰撞 **17.18 ms**；前帧末活跃 worker 数为零，本帧轮询前队列 **0.49 ms**。这证明仍未移出主线程的射程寻路能直接阻塞拖选更新。
3. 后台另一间隔 **91.29 ms**，前帧模拟 **90.55 ms**，但记录的搜索为零、移动碰撞仅 **8.24 ms**，帧末有一个 worker。现有计时没有解释剩余部分，不能将此帧武断归因于射程寻路，也不能凭队列轻量就排除线程竞争。
4. 空闲控制也有一次 **59.46 ms** 间隔，前帧模拟仅 **0.39 ms**，没有 worker。说明当前机器存在落在已计时游戏回调之外的停顿；不要用单个最大值作严格性能回归结论。

两轮对照的总体趋势没有显示后台模式系统性恶化，且没有框状态错误，但样本有限、实际战斗轨迹随调度变化，无法证明所有用户场景均无回归。本次保留生产导航和输入逻辑，新增的是诊断 PoC，没有通过移动队列调用位置掩盖整帧长耗时。

## 窗口验证限制与复现

尝试启动真实 1280×800 窗口时，macOS `com.apple.hiservices-xpcservice` 返回 Connection Invalid，18 秒启动超时后终止。因此尚未验证真实 OS 鼠标事件、窗口合成或视觉表现。

```sh
# 自动跑空闲控制及四轮 A/B；建议 --project 指向固定的项目副本。
python3 tools/profile_selection_latency.py

# 可见 PoC 自动拖选 60 秒，默认后台开启；观察同一围攻场景。
RTS_DRAG_SECONDS=60 make run RUN_ARGS='--log-file /tmp/drag-poc.log --script res://tests/selection_battle_latency_poc.gd --windowed --resolution 1280x800'

# 同步对照：同一命令前增加 RTS_ASYNC_NAV=0。
# 支持图形界面的环境可自动记录实际 frame_post_draw 间隔。
python3 tools/profile_selection_latency.py --windowed
```

可见 PoC 会自动控制游戏内部的测试指针，请直接观察自动拖选。它不会移动系统鼠标。与真实鼠标事件配送相关的问题仍需另做现场验证。
