# 围攻为何低利用率仍低 FPS：同步路径与并发 PoC

本轮没有把实时单位更新直接改成多线程，而是先调用生产导航代码验证并行性、结果一致性和主循环阻塞。PoC 见 `tests/navigation_parallel_poc.gd`，原始数据见 [parallel-navigation.json](parallel-navigation.json)。

## 帧率受关键路径限制

15 FPS 表示相邻完整帧约间隔 66.7 ms。整机 CPU 是所有核心的汇总，不能证明负责模拟/提交的一条线程还有空闲：本机 8 核，单核满载仅占整机约 12.5%。GPU 也可能在等 CPU 准备并提交指令。当前这次 15 FPS 的现场线程采样尚未取得，不能仅凭利用率就排除额外等待、旧进程或其他负载。

代码已确认的同步链是：`RtsUnit._process` → `_move_toward` → `path_to_range`/`path_between` → `path_around_units`。最后一项还可能连续尝试五种网格分辨率，成功后做逐段碰撞检查和路径简化。这些操作都在调用单位的同一帧内完成。此前优化降低了单次开销，仍未改变这个同步结构。

直接并发单位 `_process` 会引入共享状态竞争：导航缓存、空间索引、其他单位的位置、伤害/资源状态都可能被修改。`request_passage` 甚至会直接移动前方的友军。正常 SceneTree 节点访问也受引擎线程保护；不能通过关闭保护来声称实现安全并行。

## 实测并发

6 座建筑、80 个单位、150 个资源（其中 8 只鹿），固定地形和输入，每个执行通道独占一份不在 SceneTree 中的场景副本。直接调用当前 `_local_unit_grid` / `_local_unit_path`，没有用 sleep 假装计算负载。每批 80 个请求，分别在主线程、1/2/4 个 worker 上执行，正反顺序各一轮。

| 80 个请求的总计算时间，均值 | 主线程 | 1 worker | 2 workers | 4 workers |
| --- | ---: | ---: | ---: | ---: |
| 193×193 局部网格构建 | 178.25 ms | 179.46 ms | 130.54 ms | 168.92 ms |
| 恢复路径计算 | 324.14 ms | 321.01 ms | 240.28 ms | 298.98 ms |

这不是每帧固定发生 80 次寻路，也不是整场 FPS。它测量一批独立、实际导航请求的吞吐量。恢复批次有 79 条非空路径；所有线程配置的完整路径与串行结果一致，所有网格逐格一致，失败数为零。副本构建成本单独记录，恢复测试的稳定样本约 1.3/2.6/5–6 ms（1/2/4 份），首轮有冷启动开销；不能将提交任务的时间当成快照加计算的总成本。

单纯算术控制组从 1 worker 的约 29.5 ms 降至 4 workers 的约 10.9 ms（此前一轮约 7.8 ms），说明工作线程确实能够并行执行脚本。控制组主线程有一个 67.3 ms 的异常样本，原始数据完整保留，不以此宣称更高的加速比。

当前对象密集的导航代码，4 worker 反而比 2 worker 慢。源码提供了进一步排查方向：`Variant::get_validated_object()` 调用 `ObjectDB::get_instance()`，后者使用全局自旋锁；导航热循环又包含大量细粒度引擎对象属性访问和方法调用。它们可能造成共享锁、引用管理和调用边界的竞争。**这里尚未测量锁的占比，不把这项源码推断当成唯一已证实根因。**

另一个容易测错的点：本机引擎启动日志显示 `8 threads, 2 max low-priority`。默认 `add_group_task` 的 low-priority 工作最多同时用两个 worker；仅设置 tasks_needed=4 不代表四路实际并发。本报告使用 high-priority=true 的独立诊断任务，并记录不同 worker ID，验证真正的四路执行。此参数控制池内调度，不等于提升操作系统线程优先级。

## 异步与并行是两个问题

把任务提交给线程池，然后同帧调用 `wait_for_group_task_completion`，主线程仍需等批次结束。上表中的 2 worker 即使缩短了总时长，整帧仍可能卡住约 240 ms。

同样的 4 worker 恢复批次，改为每帧只查询完成状态、完成后再回收任务，批次约 325 ms 期间主循环推进 41 次，最大回调间隔 9.95 ms；提交调用约 0.011 ms。完整结果与同步计算一致。这证明可以移走主线程上的整批等待，**并未证明正式游戏可达 100 FPS**：该实验是 headless，未包含图形、正常模拟、快照应用和其他主线程工作。

## 应优先改的结构

1. 导航接收只读数据快照：地形、建筑矩形、资源/单位的位置与半径。热循环使用连续数组，减少跨引擎对象访问；必要时将栅格化/连通性内核移入原生代码。PoC 的整份 Node 副本只为重用现有算法验证，不能作为每帧大量复制的生产实现。
2. 使用有界后台请求队列，先以两个计算 worker 验证；每个单位最多保留一个当前请求，重复目标合并，玩家新指令优先。主线程不在提交当帧等待所有结果。
3. 结果带订单序号、快照版本和起点；主线程丢弃过期结果，使用前重新验证当前碰撞。移动落位、互相让路、伤害结算仍由主线程统一执行，防止位置跳变或穿越建筑。
4. 继续减少绘制调用与重绘准备开销。并行寻路不会自动消除渲染提交时间；本地引擎还明确将独立渲染线程标为 experimental，不能未经窗口稳定性测试直接打开。

本报告记录接入前的并发 PoC。后续已将拥堵恢复搜索接入正式游戏，采用纯数据快照和有界后台队列；实现、验证与剩余同步开销见 [后台恢复寻路](async-navigation.md)。

```sh
RTS_PARALLEL_HIGH_PRIORITY=1 make run RUN_ARGS='--headless --verbose --script res://tests/navigation_parallel_poc.gd'
```

所有异步任务都在退出前等待并回收；工作期间主线程不读写 worker 的副本和结果容器。测试不关闭引擎线程安全检查。
