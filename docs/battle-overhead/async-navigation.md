# 后台拥堵恢复寻路：实际游戏接入

2026-09-29，Apple M2，自带 Godot 4.7.2 debug template。正式游戏默认启用；`RTS_ASYNC_NAV=0` 保留同步对照。此次移走的是单位卡住后 `path_around_units` 的五档网格恢复搜索。`path_between`、`path_to_range`、移动碰撞和让路仍在主线程，不能将此项表述为“全部导航已多线程”或“15 FPS 已解决”。

## 为什么低利用率仍会卡

整机 CPU 利用率不能表示单条帧关键路径的余量。M2 的八核中单核饱和只占整机约 12.5%；GPU 也会等主线程完成模拟和提交。原代码在单位更新中同步构建恢复网格、执行 A*、检查路径，多个拥堵单位的开销叠加到同一帧。前一轮已验证两个 worker 对这类对象密集任务比四个更合适；本次重点是跨帧取得结果，而不是提交后立即等待。

## 实现边界

- `navigation_recovery.gd` 在主线程捕获地形字节、建筑矩形、资源/单位位置和半径。只存值数据；半径用 Float64 保留原精度。worker 独占快照、AStarGrid2D 和输出，不访问 live SceneTree、共享导航缓存或空间索引。与同步路径共用圆形栅格化、出口筛选、连通性和矩形相交的纯函数。
- `navigation_jobs.gd` 限制两个活跃计算、128 个等待项，每单位只保留当前请求；派发使用 1 ms 软预算，单次快照不可抢占。超容量请求继续按原退避重试。取消移除等待项，运行中的旧任务完成后回收。请求两秒后过期，避免闲置单位长期持有结果。
- 主循环只对已经完成的任务调用 wait/reap，不等待未完成任务。退出或重置场景时才允许等待正在运行的最多两个任务，释放线程池记录。
- 新订单增加序号并取消旧请求；主线程领取结果时检查订单、阵营、结构版本、目标变化、半径/海陆属性和起点偏移，并用当前位置、当前鹿群和单位重新检查第一段碰撞。后续段仍由原有移动碰撞控制。没有将单位位置设置为快照位置。
- 计算期间单位继续使用已有路径。结果延迟是明确的取舍；普通寻路仍然同步。同步模式保留供对照及回归，快照输入适配与原 live-object 输入必须持续做差异测试。

## 最小 PoC 与正确性

`tests/navigation_async_poc.gd`：6 建筑、80 士兵、150 资源，其中 8 只鹿。80 条完整恢复路径与同步实现相同，148,996 个网格点逐格一致；另外覆盖海陆地形、友军/敌军城门、非整数半径和初始重叠。共 23 项检查通过，包括新指令、结构变化、移动目标、单位位移、鹿移入路线、单位死亡、重置与重用、队列容量/合并，以及真实 `_move_toward` 发起请求后绕过敌人抵达目的地。每步验证速度上限和碰撞。

最新单次诊断：同步批次 **114.76 ms**；快照内核在主线程串行执行 **128.67 ms**，因此不声称纯计算更快。后台批次墙钟 **343.79 ms**，跨 **44 帧**，主线程累计 **46.04 ms**，单帧处理最大 **1.28 ms**。这里的主线程时间包含快照、派发、轮询、回收和现场结果校验；早期只计派发/回收的约 20 ms 数字不作为完整结果。快照捕获累计 11.57 ms。原始数据见 [async-navigation.json](async-navigation.json)。

12 个导航/鹿群/施工/密集编队相关测试通过，最终快照半径精度及领取计时调整后再次运行完整异步 PoC，23 项通过。测试 runner 显式指定可写日志路径，避免受限环境的 user:// 日志权限导致假失败。

## 真实围攻逻辑的四轮对照

`tests/navigation_async_battle_poc.gd` 使用实际游戏和原 2.5D 展示场景：生成地图、80 人集中进攻、6 座新增建筑、8 只新增鹿，保留原地图实体。每次预热 2 秒，再采集 10 秒模拟，按同步/后台/后台/同步串行执行，关闭 profiling。计时从 process_frame 到高 process_priority 的末尾节点，覆盖主线程游戏模拟及后台结果应用。

| 主线程模拟耗时 | 同步，第 1 / 4 轮 | 后台，第 2 / 3 轮 |
| --- | --- | --- |
| 平均 | 14.39 / 14.92 ms | 12.90 / 12.87 ms |
| P95 | 46.14 / 46.13 ms | 27.21 / 26.15 ms |
| 最大 | 126.05 / 105.44 ms | 68.99 / 64.01 ms |
| 建筑伤害（含预热） | 1060 / 1150 | 1160 / 1230 |

后台各轮接受 219 / 217 个结果、丢弃 3 / 3 个过期或不再安全的结果；等待队列最大 4 / 6，实际战斗并未累积成 80 请求的人工批次。伤害量证明战斗持续推进，不证明两种调度的所有位置轨迹完全相同。原始四轮数据见 [async-battle.json](async-battle.json)。

这是 **headless 主线程模拟耗时，不是实际窗口 FPS**。当前受限环境的 macOS 窗口启动被 XPC 服务拒绝，因此尚未完成可见窗口的 FPS 和长时间视觉验收。不得由表中数值宣称稳定 60 FPS。profile 定位运行仍观察到同步 `path_to_range` 冷启动长调用；渲染提交也没有被此次后台搜索消除。

## 复现

```sh
python3 tools/check_navigation.py --tests navigation_async_poc
RTS_ASYNC_NAV=0 make run RUN_ARGS='--headless --log-file /tmp/sync-siege.log --script res://tests/navigation_async_battle_poc.gd'
RTS_ASYNC_NAV=1 make run RUN_ARGS='--headless --log-file /tmp/async-siege.log --script res://tests/navigation_async_battle_poc.gd'
# 可见场景默认启用后台恢复；同一条命令前加 RTS_ASYNC_NAV=0 可对照。
make run RUN_ARGS='--script res://tools/battle_deer_poc.gd --windowed --resolution 1280x800'
```
