# 密集建筑与多任务寻路排查

2026-09-29，Godot 4.7.2，macOS arm64，无窗口逻辑验证。基线为 `fc65f03`，在独立项目中运行相同 PoC；工作区原有的渲染和设置改动未包含在本次修改中。

## 复现方法

先对原代码运行新增 PoC，保存失败输出，再逐项修复。排查期间继续增加窄缝、围堵、缓存失效和真实任务队列案例；最终版本的 PoC 再回放到原始代码，避免只比较不同版本的测试。

| `navigation_dense_poc.gd` | 162 | 85 | 0 |
| `navigation_tasks_poc.gd` | 31 | 15 | 0 |
| 合计 | 193 | 100 | 0 |

[修复前日志](dense-baseline/) · [修复后日志](dense-final/)。检查数包括同一场景的路线、实际到达、队列和碰撞约束，不代表 193 个独立根因，也不是所有地图和状态的穷举证明。

另有 `navigation_grid_raster.gd` 的 40 组优化回归：覆盖水陆、两方阵营、五种半径、全地图及带偏移的局部网格，逐格比较 **65,644** 个位置，快速网格构建与原碰撞规则全部一致。这些检查不计入上表的原版本对照。

## 已修复的原因

| 原因 | 复现与修复 |
| --- | --- |
| 交互圆周只按来路取八个点，全部可能落在建筑碰撞框内 | 八种斜向接近农田；新增固定方位和建筑边缘与交互圆的交点。真实农田作业恢复。 |
| 维修落点比交互距离缩小 0.25 像素，实际要求站进建筑 | 农田、铁匠铺、修道院、城堡、奇观的维修及后续移动队列。候选落点使用与移动一致的到达容差。 |
| 精细寻路只搜索起终点外扩 150 像素，超过 16,000 节点直接放弃 | 唯一入口在远处、4000×2000 地图斜向长路。小范围搜索失败后继续尝试全地图细网格；局部、全地图网格各最多缓存四份，按阵营、体型、水陆区分，障碍变化时失效。 |
| 建筑合法窄缝仍可能落在细网格采样点之间 | 五种半径 × 三种额外净空（1、4、10 像素）× 三种建筑偏移，共 45 张地图，各检查路线及实际到达。按建筑外扩边角补充可见路径。 |
| 调整被阻挡的落点时，用粗网格连通性否决精细路线 | 资源另一侧有合法细缝，点击资源却被改到墙的近侧。落点验证使用完整寻路能力。 |
| 固定 24 像素的移动边界与实际单位半径不一致 | 四条地图边缘的交互目标。移动及落点钳制统一按单位半径处理。 |
| 攻击地面使用点到点寻路，建筑内部目标永远不可占据 | 对被建筑覆盖的位置攻击地面，改为寻找到射程内的合法位置。 |
| 资源重叠时的临时脱困许可被写进共享通行网格 | 同体型的另一单位复用错误网格。共享栅格构建时禁用这项与当前单位位置有关的许可，实际脱困保留。 |
| 固定单位围堵超过局部搜索范围；局部网格漏掉拥堵细缝 | 大型 U 形守军围堵、八名工人对向穿过建筑通道。持续失败后逐级细化、扩大避障搜索，并保留重试退避。 |
| 线段采样可能跨过擦过圆或建筑角落的短交叉段 | 资源移动不足导航刷新阈值后封住细缝。增加圆及矩形的线段相交检查；资源任意位移清除边角可见性缓存。 |

## 多任务和回归

- 1、12、48、96 名工人，96 栋建筑，最多 768 项施工任务加后续移动；要求相应建筑全部完成、全部队列清空、全员离开工地且无瞬移。
- 1、4、8 名工人分别操作各自的农田；遵守游戏“一块农田一名工人”的规则。
- 商人完成多次往返；被删除的排队施工目标跳过后继续移动。
- 12 项维修被整面墙封住时保留任务、不隔墙工作；拆墙后全部维修及后续移动完成。
- 施工、拆除和小幅资源移动后的导航缓存重新验证。
- 既有寻路、施工、编队窄口、多人编队、经济、野猪脱困等回归，见 [回归结果](dense-regressions.json)。

已完成指令的空闲友军可以为后来者让路，因此压力测试检查任务完成和离开工地，不要求永远停在精确终点。排查时纠正了这类测试误判，没有把让路行为计为寻路故障。

## 性能处理与限制

交互寻路先检查所有可直达落点，再尝试粗网格路线，最后才启用精细兜底；避免一个坏候选让每个工人重建大网格。附近小队复用覆盖起终点的局部细网格，局部失败才扩大到全地图。静态连通区域按导航版本缓存，提前拒绝不相连的起终点。局部拥堵搜索先排除没有前进意义的出口，精细及扩大搜索仅在持续失败后触发。

精细网格直接根据地形、建筑和资源几何形状写入阻挡区域，避免对地图每个细格重复查询空间索引。上面的逐格对照验证了水陆、圆形资源、矩形建筑、友方／敌方城门和地图边界的碰撞一致性。

本机单次串行测量，未开启 profiling；单位轨迹会随修复变化，因此这是场景对照，不是相同轨迹的微基准。耗时为毫秒，不代表窗口渲染 FPS。[原始性能日志](dense-performance/)

| 场景／指标 | 原版本 | 最终版本 |
| --- | ---: | ---: |
| 400 独立单位，平均模拟步 | 14.33 | 12.80 |
| 400 独立单位，P95 | 19.92 | 12.38 |
| 400 单位编队，集中下令 | 376.2 | 500.6 |
| 400 单位编队，平均模拟步 | 94.4 | 104.9 |
| 400 单位编队，P95 | 174.2 | 160.8 |
| 400 单位编队，最大模拟步 | 755.2 | 849.9 |
| 400 单位战斗，平均模拟步 | 6.20 | 6.13 |

精细网格优化消除了排查中出现的约 1.2 秒集中下令回退，但最终编队下令和平均模拟步仍比原版本慢。新增可达性兜底及更严格的碰撞检查有成本，不能把正确性修复表述成全面加速。400 人脚本是性能基准；任务全部完成的断言来自前述 96 人施工和既有窄口测试。

这些改动仍为同步搜索，首次创建大范围细网格或集中处理复杂拥堵仍可能造成帧峰值。动态避障最大窗口为单位周围 768 像素；边角兜底针对建筑矩形，任意亚像素地形／资源迷宫没有完备性保证。没有宣称所有场景达到固定 FPS，也未做窗口内手动游玩验证。

## 重跑

```sh
python3 tools/check_navigation.py --tests navigation_dense_poc navigation_tasks_poc navigation_grid_raster
python3 tools/check_navigation.py

# 单独采样密集施工；计时运行不要与其他测试并行
RTS_TASKS_DENSE_ONLY=1 RTS_TASKS_COUNT=48 python3 tools/check_navigation.py --tests navigation_tasks_poc
RTS_NAV_PROFILE=1 RTS_TASKS_DENSE_ONLY=1 RTS_TASKS_COUNT=48 python3 tools/check_navigation.py --tests navigation_tasks_poc
```

`--path` 可指定基线项目，`--output` 可保存独立日志，`--godot` 可指定引擎。默认完整检查包含本次两个 PoC 和网格一致性回归。
