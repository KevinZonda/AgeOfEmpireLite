## 已复现的问题

| 现象和 PoC | 原因 | 修复 |
| --- | --- | --- |
| 半径 28 的单位选择 50 宽窄口，最终停在 `(586.65, 275)`；下方实际存在宽路 | 搜索使用固定外扩，实际移动按单位体型碰撞 | 按阵营、体型、水陆缓存通行网格；验证网格连接段和路径端点 |
| 障碍与地形之间有合法细缝，但搜索返回空路径 | 50 像素格子的中心没有落在细缝里 | 粗网格搜索失败后，使用有范围和节点数量限制的精细网格；移动与交互寻路共用此兜底 |
| 西侧单位点击资源中心，落点却在东侧 `(661, 525)` | 最近落点的环形扫描总从东侧开始 | 等距候选优先选择单位来路一侧，PoC 落点改为 `(589, 525)` |
| 攻击目标距离内存在合法位置，单位却完全不动 | 只尝试攻击范围圆周上的八个位置 | 增加范围内部候选；验证到候选的实际路径 |
| 更新一个远处障碍后，编队部分单位永远不能结束指令 | 重算重新分配槽位，单位仍保存原来的 `destination` | 保留槽位分配；调整受阻落点时同步单位的指令目的地 |
| 新障碍封死道路后，部队继续追逐不可达的旧落点 | 共享目标已调整，成员最终落点未随之更新 | 将成员落点同步到可达一侧，结束当前移动 |
| 近距离平移、纵队／密集队形中互相堵住 | 当前队友位置干扰最终落点选择；槽位可能重叠；前后排分配会交叉 | 静态落点检查、槽位间隔与预留、按兵种角色约束的最小总距离分配 |
| 窄口边来回晃动，或穿过窄口后仍不能完成命令 | 路点偏移和游标推进不一致；只检测位置变化，晃动也被视为前进 | 游标根据实际进度推进；完整体型检查；检测到路点的距离是否改善；受阻成员独立重算 |
| 已到达的友军封住后排；敌方静止单位形成 U 形围挡 | 只做短距离试探，反复重算的全局路径仍忽略单位障碍 | 空闲友军让路；互相卡住的移动友军按固定优先级短暂让路；固定单位障碍使用局部精细寻路。敌军和坚守单位不会被推走 |
| 脱离编队或先停下后，附近单位突然更容易被卡住 | 编队碰撞间距先缩到 70%，退出编队后突然恢复 | 移动和停下使用一致的单位碰撞间距 |
| 速度 260 的单位，120/60/30/20 Hz 下每秒分别走 260/260/216/144 | 每帧位移直接裁成半径的 0.6 倍 | 分步碰撞检测后，同组测试均走约 260；异常长帧最多处理八个子步 |
| 资源在同一格内移动 46 像素，导航没有失效 | 只比较资源所属的 50 像素格子 | 资源移动按 8 像素位置量化触发更新；实际碰撞始终使用当前位置 |
| 精确接触地图下边界时越界访问第 600 个地形元素 | 最大行／列未限制在数组范围内 | 限制地形检测的最大索引 |

## 覆盖范围与回归

- 四种队形 × 八个方向 × 近／远两种距离，均要求所有成员实际完成命令。
- 半径 10、12、18、24、28 的单位，各运行 20 张随机障碍地图；检查每段路径合法且最终到达。
- 一格、两格、三格窄口；短距离移动；资源移动；落点被覆盖；道路被封死；排队指令与重新指定目标。
- 水陆隔离、友方／敌方城门、地图边界、格内合法起点、细缝通道、攻击范围内部落点。
- 敌方坚守单位形成的 U 形围挡：须绕行抵达，且守军位置不变。
- 现有 `navigation`、`navigation_routes`、`navigation_replanning`、`group_chokepoint`、`group_mass_chokepoint`、`group_multiplayer`、`terrain_selection_follow`、`extended_systems`、`economy_siege_controls`、`smoke` 均通过。[回归清单](regressions.json)

斜坡测试原先把每帧最多移动 `radius × 0.6` 当作“不瞬移”的条件，恰好固定了本次发现的减速错误；现在按 `speed × delta` 检查位移上限，保留斜坡移动、单位重绘、选择圈跟随的原有断言。

## 重现

```sh
# 新增 PoC
python3 tools/check_navigation.py --tests navigation_poc navigation_poc_matrix

# PoC 与十项现有功能回归
python3 tools/check_navigation.py

# 400 单位性能测试；不要与其他测试并行测量
RTS_BENCH_STEPS=180 python3 tools/check_navigation.py \
  --tests performance_navigation performance_400 performance_combat
```

默认日志与 JSON 结果写入 `.godot/navigation-checks/`。可用 `--output` 指定目录、`--godot` 指定引擎、`--path` 指向隔离的原版本项目。脚本检查退出码、脚本错误和失败标记，避免将 Godot 的“断言失败但退出码为零”误报为成功。

## 性能与限制

同机、同脚本的单次无窗口运行，未开启 profiling。修复会改变实际移动轨迹，因此这不是严格相同轨迹的微基准，也不代表真实窗口 FPS。

| 指标（毫秒） | 原实现 | 修复后 |
| --- | ---: | ---: |
| 400 单位独立移动，平均模拟步 | 5.67 | 5.25 |
| 400 单位独立移动，P95 | 4.81 | 4.68 |
| 400 单位编队，集中下令 | 44.5 | 214.1 |
| 400 单位编队，180 步平均 | 44.0 | 40.6 |
| 400 单位编队，P95 | 87.6 | 76.4 |
| 400 单位编队，最大单步 | 246.8 | 522.6 |
| 400 单位战斗，平均模拟步 | 2.24 | 2.26 |

持续模拟均值与 P95 没有退化，但更严格的路径、落点验证和拥堵恢复增加了集中下令成本及单步峰值。214 ms 的下令耗时低于项目 250 ms 目标；约 41 ms 的平均模拟步仍在 40 ms 目标附近，523 ms 峰值说明集中恢复仍可能引起短暂停顿，需要后续将重规划分摊到多个模拟步。不能把本轮正确性通过理解为所有帧都能满足 30 Hz。

[原始性能日志](performance/)

精细静态搜索限制在起终点包围框外扩 150 像素、最多 16,000 个节点；单位避让搜索限制在局部区域。超出范围的极端细缝／迷宫仍可能需要更完整的导航网格。资源移动的小幅更新会合并，阻挡发生时仍有精确碰撞和重算兜底。100 人既有窄口测试要求全员穿过窄口；400 人测试是性能基准，不能当作所有人最终到达的证明。本轮未做可视化手动游玩。
