# 运行时开销排查与优化

2026-09-29，在 Apple M2 / macOS 上使用本地 Godot 4.7.2 `template_debug` 修复版。基线为 `f9f7379`，保存在独立项目中；前后使用相同基准，串行交替运行三轮，关闭 profiling 后计时。[全部运行数据](timings.json)。

## 主要原因和修改

1. **路径验证重复检查同一批障碍。** `_static_segment_clear` 已经对整段路径检查建筑矩形和资源圆，随后又逐点调用完整 `can_occupy`。现在逐点阶段只检查地形，保留建筑边界、资源擦边和重叠脱困规则。初始 400 人编队 profiling 中，90 步有约 62 万次占位检查；A* 本身累计只有约 15 ms，主要耗时在外围几何检查。
2. **局部避障网格重复扫描邻域。** 最宽恢复网格有 37,249 个格点，原来每格分别查询地形、建筑、资源和单位。现在复用静态几何栅格化，再按附近单位的覆盖范围填入障碍。驻军不参与地面碰撞；已有重叠允许向外移动的规则保持一致。
3. **空间查询范围过宽。** 原碰撞查询按所在桶向四周扩展整圈，小单位也通常扫描九个桶。现在只访问碰撞范围实际覆盖的桶，减少字典查找和邻居遍历。
4. **无关的资源移动触发所有小队重新寻路。** 编队原来遇到导航版本变化就无条件 `_replan`。现在清除几何缓存，验证剩余路线及各成员终点；路线仍有效时保留。空路线、受阻路线和调整过的目标仍会重新评估。诊断窗口循环时，曾观察到 34 个小队每帧重算，以及一次约 2.7 秒的落点搜索。
5. **寻找落点时做了多余的准备和搜索。** 不要求可达性的查询延迟创建通行网格。全地图兜底改为距离从近到远检查，找到第一个可达点即返回，避免按行扫描过程中对越来越近的多个点反复寻路；等距离仍按原来的行、列顺序选择。

没有降低碰撞精度、减少寻路搜索范围或降低模拟更新频率。新增 `move_step`、`recover_building_overlap` 和 `path_around_units` 可选计数，默认关闭。

## 三轮对照

以下每一项取三轮中位数，单位为毫秒。编队基准为 400 人、34 个小队、90 个 1/30 秒模拟步；独立移动为 400 人、180 步；战斗为 200 对 200、90 步。这些是 CPU 场景基准，不包含完整的 UI、AI 和窗口渲染，不能直接换算成游戏 FPS。

| 编队集中下令 | 157.1 | 123.1 | 22% |

`performance_400.gd` 固定全局随机种子；地图种子仍为 4242。延迟创建导航对象会改变依赖实例 ID 的避让次序，因此这里比较同一场景，不声称逐步轨迹完全相同。战斗各轮均为 1,204 次攻击、14,448 生命损失、400 个幸存单位。

## 正确性验证

- 静态和动态栅格共 76 组、654,352 个位置，与独立的实际占位判定逐格比较，覆盖水陆、阵营、体型、偏移网格、地图外区域、单位／资源重叠和驻军。
- 新增编队回归覆盖远处资源移动不重算、路线和槽位保留、新建筑强制绕行、空路线重试、目标受阻及清障后的恢复。
- 新增全地图落点兜底回归，检查最近可达点及等距离选择顺序。
- 完整导航回归的 17 个脚本全部通过，退出码为 0，无脚本错误或断言失败。[结果记录](regressions.json)，通过 `tools/check_navigation.py` 可重跑。

少数脚本仍有退出时 ObjectDB 回收警告。原版本施工测试也会报告该警告；本次对经济测试的 `--verbose` 抽查显示残留对象为 `AudioStreamWAV` / `AudioStreamPlaybackWAV`。这次没有修改音频生命周期，也没有把这些警告计为已解决。

## 仍存在的限制

400 人密集编队平均 53 ms/步，仍未达到项目的 40 ms 目标。本次三轮中最慢一步为 1061.9 ms；同步精细搜索、复杂拥堵和集中重试仍可能造成卡顿。有窗口的密集移动诊断也出现长帧，本次没有取得完整、可比较的真实窗口 FPS 结果，不能宣称已经消除卡顿。

迷雾单次更新仍约 14 ms，导航障碍和空间索引仍会整体刷新。后续应优先测量并处理每帧搜索预算和障碍局部失效；本次将修改集中在已确认的重复工作上。

## 野生动物缓存失效与卡住重试（2026-09-29 第二轮）

用户报告"玩一会儿突然很卡，过一会儿又恢复"。真实对局 headless 逐帧计时（4 玩家 FFA、种子 4242、2400 帧，诊断脚本 `tests/diag_frame_spikes.gd`）确认：平时平均 8.7 ms/帧、P99 约 10 ms，但间歇爆发 100–376 ms 的单帧尖刺。

**原因链。** 地图上的鹿/野猪/羊每帧游走，`resource_moved` 对每次移动做全图 `invalidate_obstacles`：实测 2400 帧中 2399 帧障碍版本号跳变，精细网格、连通标记、角点图、空间索引全部活不过一帧。此时若村民的采集/建造目标不可达（实测卡住的多为 `order=gather/build` 的村民），其指数退避重试的 `path_to_range` 每次都要重建全图精细网格（单帧最多 23.2 万格）、对 11.6 万格做 GDScript 洪泛连通标记、并按候选逐次构建局部精细网格与角点可见性搜索——单次重试 142–384 ms。退避到期再爆一次，就是"卡一阵、恢复、又卡"的周期。

**修复（`scripts/world/navigation.gd`）。**

1. 活着的野生动物（deer/boar/sheep）视为动态障碍：`resource_moved` 只做空间索引的增量桶迁移（与 `unit_moved` 相同），不再全图失效；障碍签名不再包含野生动物位置。碰撞精度不变——`can_occupy` 与线段扫掠本来就按实时位置查询资源。静态资源（树、矿）移动仍走原有全量失效，所有既有语义不变。曾尝试把野生动物从网格栅格化中排除，但 400 人编队基准平均步耗时从 64 ms 涨到 75 ms（规划路径穿鹿引发拥堵抖动），已回退；网格仍按建网时的野生动物位置栅格化。
2. `_fine_static_path` 在世界精细网格已有连通标记时，先比较两端附着格的连通分量；证明不连通就直接跳过逐候选的本地网格构建和精细 A*，只留精确角点兜底。
3. `path_to_range` 的 refine 阶段把角点可见性兜底限制在最近的 4 个候选（`MAX_RANGE_CORNER_ATTEMPTS`）；角点 A* 对不可达目标是 O(角点数²) 的逐候选开销，是修复缓存失效后剩余的主要成本。

**PoC（`tests/navigation_wildlife_churn_poc.gd`，已加入 `tools/check_navigation.py`）。** 隔着全高山脉的矿点 + 远处游荡的鹿：修复前 10 次失败重试在世界静止时 1422 ms、鹿移动时 3838 ms，30 步游荡使障碍版本号 2→32 并清空精细网格；修复后 290/295 ms，版本号与缓存保持不动，移动中的鹿仍即时阻挡碰撞、留在空间索引中。

**端到端结果。** 同一诊断场景：障碍版本号跳变 2399/2400 帧 → 8/2400 帧；最慢帧 376 ms → 63 ms（剩余尖刺是建筑完工等真实结构变化后的首次缓存重建）。CPU 基准三轮交替 A/B（`performance_400`，RTS_BENCH_STEPS=90）：修复前 command 205–213 ms / 平均步 64.0–67.8 ms / P95 100–114 ms，修复后 205–207 ms / 63.8–64.6 ms / 109–133 ms，无回归；`performance_combat` 峰值 208.6 ms → 143.5 ms。

**回归。** 导航套件 28 个脚本全部通过。`smoke` 在 `smoke.gd:55` 光标断言失败、`navigation_range_corner_poc` 的 `range_candidates_reuse_origin_visibility` 失败，两者在未修改导航的对照代码上同样失败，属工作区既有问题。

**仍存在。** 单次不可达重试仍约 30 ms（候选枚举 + 限频后的角点兜底）；卡住单位不会放弃目标，只会退避重试。迷雾每 0.15 s 约 14 ms 的全量更新与 AI tick 的寻路簇未处理。
